# 2ⁿ − 25 Prime Search

A static data site for the search for primes of the form 2ⁿ − 25 ([OEIS A379020](https://oeis.org/A379020)),
in the spirit of mersenne.ca: one page per exponent for every odd n below 10⁷, plus project-wide status,
sieve depth, known primes and a form to upload results. It is served by GitHub Pages straight from this
repository; there is no server-side code except the small upload Worker in `worker/`.

| Page | What it shows |
|---|---|
| `index.html` | Status: the big chart of every odd n below 10⁷, key numbers, active range, outlook, frontier and PRP results since `status_since`, latest results, largest primes |
| `ranges.html` | Work per 1M / 0.2M of n: sieve depth, P-1, PRP, unresolved |
| `exponent.html?n=…` | One n: status, factors, PRP residues, proof, history, neighbourhood |
| `sieve.html` | Sieve depth by range, candidates left, P-1 factor sizes, siever versions |
| `primes.html` | Every known n, against the expected count |
| `history.html` | The whole story: frontier and work per day since 2024, records, month by month, milestones, timeline |
| `join.html` | How to help, example work lines, upload form |

## Layout

```
*.html               the seven pages (generated by tools/make_pages.py from pages/*.body.html)
assets/              CSS and one script per page; no libraries
content/site.json    facts written by hand: plans, sieve assignments, benchmarks, notes
content/sieve_layers.json   smallest-factor layers of the ranges without Mass Prime Siever output
content/trial_left.json     odd n in 3.6M–5M with no factor below 10^7 (for ranges sieved in part)
data/                written by tools/build.py; the pages read only these JSON files
data/n/<x.xx>.json   per 0.01M of n: sieve survivors and every P-1 and PRP record (s0: first-sieve survivors)
data/f/<x.xx>.json   per 0.01M of n: every sieve run over those n, and every sieve factor above 10^7 under the run that found it first
archive/             local copy of what build.py needs from the project archive (not published)
archive/pm1_splits.json     prime factors of composite P-1 results, worked out once by build.py
archive/prptop.json  Top PRP rank of each known prime on PRP Records, read once a day
tools/sync_archive.py       refreshes archive/ from the archive drive
tools/build.py       reads archive/, checks it, writes data/
tools/pull_submissions.py   copies uploads from the Worker into archive/Submissions
tools/prptop_ranks.py       reads the Top PRP ranks from PRP Records into archive/prptop.json
tools/auto_update.py        what the scheduled task runs: new uploads -> build -> push data/
tools/make_pages.py  rebuilds the HTML pages after a change to pages/ or the shared header
tools/sieve_layers.c        writes content/sieve_layers.json (and the n list for trial_left.py)
tools/trial_left.py  writes content/trial_left.json from that n list
worker/              Cloudflare Worker that receives uploads (deployed separately)
```

## Updating the site

On the PC that holds `archive/`, a scheduled task does this every 15 minutes (see *Updating by itself*
below). By hand:

```
python tools/sync_archive.py                  # when the archive drive is attached
python tools/pull_submissions.py --delete     # only if people uploaded results
python tools/build.py                         # reads archive/, writes data/
git add data content && git commit -m "Update data" && git push
python tools/sync_archive.py --back           # when the drive is attached: copy saved uploads to it
```

On Windows, write `py -3` instead of `python` if `python` opens the Microsoft Store.

All scripts use only the Python standard library. The project archive lives on a drive that is not
always attached, so `build.py` reads `archive/` in this folder, a copy of just the files it needs:
sieve output, candidate lists, and P-1 and PRP result lines for each range folder, plus the uploads.
No proof file is copied. `sync_archive.py` refreshes that copy; it copies a file only when it is new or
changed, never deletes anything, and leaves alone (and lists) a file that is newer here than on the
drive. Range folders are named `3.4M-3.6M` in the copy instead of `3.4M~3.6M`, because some tools
cannot open a path with `~` followed by a digit. `build.py --archive <folder>` reads another copy.
`archive/` is not published.

`build.py` prints a summary. Anything it could not use or did not trust is listed in
`build_report.txt` next to `data/`; that file is not published.

### Updating by itself

On the PC that holds `archive/`, a scheduled task runs `tools/auto_update.py` every 15 minutes while
someone is logged on. It saves new uploads (`pull_submissions.py --new-only`: two key lists a run when
nothing is new, about 200 a day, inside the free plan's 1,000 a day), runs `sync_archive.py --back`
when the archive drive is attached, once a day reads the Top PRP ranks of the known primes from PRP
Records (`prptop_ranks.py`: one request for the list of 2ⁿ − 25, checked before it is saved; a failed
read is tried again three hours later), once an hour reads the progress of the Prime95 PRP run on this
PC (`live_prp.py`, below), and stops there if nothing `build.py` reads has changed. Otherwise
it rebuilds `data/`, checks that no known prime, PRP test, P-1 factor, resolved n or sieved range went
missing (partial sieves included), that no sieve depth shrank and that the frontier did not move back,
and then commits `data/` alone (message "Update data…", by RP-12000 with GitHub's no-reply address)
and pushes it. Data that fails a check is not published: `data/` is put back and the next run waits
for new input or a new commit.

It never commits anything outside `data/` and never pushes a commit it did not make. It does nothing
while files outside `data/` have uncommitted changes, or while this copy has commits of someone else's
that are not on GitHub yet, so work on the code is never published by it. Once such work is pushed (or
undone), the next run catches up. It writes what it did to `auto_update.log` (a problem that keeps
happening is written once) and keeps its state in `auto_update_state.json`; neither is committed.

`live_prp.py` only reads Prime95's `results.json.txt` (in `Desktop\WMC` of the user running the task):
it writes, moves or locks nothing in that folder and copies nothing to the archive drive. Of each
2ⁿ − 25 PRP result it keeps what the pages show (n, result, Res64, FFT length, proof power, program and
time) in `live/prp_progress.json` here, which is not committed; a last line that Prime95 is still
writing waits for the next read. `build.py` adds these results to the archive's, for a range whose
`PRP/results.json.txt` is not in the archive yet; once it is, each test counts once. A probable prime
among them is shown as being verified until its result is in the archive or n is in
`confirmed_primes`.

```
schtasks /Query /TN "2n-25 site auto-update" /V /FO LIST    # is it there, when did it last run
schtasks /Change /TN "2n-25 site auto-update" /DISABLE      # pause it (/ENABLE to resume)
py -3 tools\auto_update.py --dry-run                        # see what it would publish now
```

The task was made with PowerShell's `Register-ScheduledTask`: action `pyw.exe -3
tools\auto_update.py` in this folder (no window), repeat every 15 minutes, also on battery, one run at
a time. `schtasks /Delete /TN "2n-25 site auto-update"` removes it.

### What build.py checks

* **Sieve output** (Mass Prime Siever 12.0 `results.json`, any number of machines or p slices under
  `Ranges/<range>/TF/`): every factor in `factored` must lie in the file's `[P0, P1)`, divide 2ⁿ − 25,
  be prime (exact test), and not be 2ⁿ − 25 itself. An n counts as removed only when one of its factors
  passes; otherwise it stays a candidate and is listed in the report. Every odd n must appear exactly
  once in `prp` or `factored`, the p ranges of the slices must join up without gaps, and every survivor
  must be in `Candidates/*.txt`, or the report says which n still need a PRP test. Each range folder
  holds its own slices (`TF/p 10T~12.5T/` and so on); a `siever.log` copied into several range folders
  has its run time shared between them. A range whose slices do not start at p ≤ 7 yet is sieved *in
  part*: its checked factors strike n out and the pages show the p range done, but it counts as sieved
  only once a slice from p ≤ 7 joins up with the rest.
* **Every factor is kept**, not only the one that struck n out: `data/f/` lists each checked factor
  above 10⁷ under the slice that found it (its p and n range, when the run ended, who ran it, whether it
  was uploaded), and the exponent page adds the ones below 10⁷ by trial division. A factor that several
  slices list is shown once, under an upload that the archive keeps too (so it keeps the uploader's
  name), else the range folder's own slice, else the earliest other upload.
* **Every sieve run is listed**: each slice in `data/f/` also carries its run from the siever log
  (`prog`, start `st`, run time `s` in seconds, and `rn`, all the n the run sieved), so the exponent
  page's History lists one row per run, the way mersenne.ca lists trial factoring. A run split into
  several uploads or range folders is one entry per file. The old sievers' slices list their stations
  in `runs`. An old `log.txt` holds every launch of its task, and the total each launch prints counts
  that launch only, so the run time adds up the launches.
* **Ranges sieved twice.** Below n = 3.6 million the old CPU sievers (2ⁿ−25 Siever 1.0 to 3.0) ran
  first, to depths between 10⁷ and 2³², and P-1 and the PRP tests ran on what they left; Mass Prime
  Siever 12.0 then sieved the same n again, to 10¹¹. A range folder with both keeps both: the old files
  are its first sieve (`sieve_before` in `ranges.json`, `s0` in `data/n/`, `depth_before` in
  `progress.json`), Mass Prime Siever its second (`sieve`). Each factor is credited once, to whoever found
  it first: one that divides a P-1 factor of the same n stays with P-1; one below the first sieve's depth,
  of an n the first sieve removed, stays with the first sieve and its date (a slice of its own in
  `data/f/`, marked `before`); only the rest are listed under the second sieve. Where the first sieve
  wrote no factor files (`sieve_factors_not_kept` in `content/site.json`: 3.2M to 3.6M), its factors
  above 10⁷ count as the second sieve's. The report lists any n that the second sieve kept although the
  first removed it, and any n that the first left although a prime below its depth divides it. A range
  counts as done on the day of its last P-1 or PRP result, not on the day of the second sieve.
  `pm1.after_sieve` in `ranges.json` (`pm1_after_sieve` in `summary.json`) counts the n with a P-1
  factor that the second sieve left; the Ranges page counts the others under the sieve.
  `sieve_targets` in `content/site.json` sets the target depth for a span of n (10¹¹ below 3.6 million;
  `sieve_target` everywhere else).
* **Prime95 results**: duplicate lines, n outside their range folder, unknown work types.
* **P-1 factors** must divide 2ⁿ − 25 and lie above the sieve depth of their range. When a run finds
  two or more primes at once, Prime95 reports their product; `build.py` splits it by replaying the
  run's P-1 in small steps on that number alone, and keeps the result in `archive/pm1_splits.json`
  (the first build takes about a minute, later ones a few seconds). The exponent page shows the
  product and its primes, and the statistics count primes. A result line that reports several factors
  keeps all of them.
* **Uploads**: a probable prime reported by someone else is shown as *being verified* until its n is
  added to `confirmed_primes` in `content/site.json` (after re-running the test) or a P result for it
  appears in the archive. A claimed probable prime with a prime factor below 10⁶ is ignored.
* **Uploaded sieve output** (`Submissions/<id>/TF/`) is merged into the range folders that have Mass
  Prime Siever output of their own, and every factor is checked the same way. Its checked factors
  always strike n out. It counts toward the sieve depth only if it found at least 80% of the factors
  expected for its p range (about odd n × ln(ln P1 / ln P0); a slice that starts below 1000 is judged
  by its factors above 10⁶), or once its id is in `accepted_sieve_uploads` in `content/site.json`;
  otherwise the report lists it. Who found a factor
  above 10⁷ is shown on the exponent page. An upload whose p and n ranges a slice in the archive
  already covers is not merged a second time, so a result filed in the archive is not counted twice;
  its factors still carry the uploader's name.

## Uploads

The Join page posts `results.json.txt` lines to the Worker in `worker/`, which checks each line, keeps
it in Workers KV, and asks for the proof file when a line reports a probable prime. `pull_submissions.py`
saves each upload as `Submissions/<id>/submission.json` (and `<n>.proof`) in `archive/`, checks proof
files against the MD5 in their result line, and with `--delete` removes from the Worker only what it
saved and checked.

Sieve output (Mass Prime Siever `results.json`, p below 2⁵³, plus `siever.log` for the run time) has its
own form. The browser checks every factor and that every odd n appears once, and refuses the file if
anything is wrong. It then sends one line `n p p …` per odd n that has a factor, in uploads of at most
3 MB split by n. The Worker stores the lines once and checks every factor again in slices of 150 factors
(`/tf/begin`, `/tf/check`, `/tf/finish`), which keeps each request well inside the free plan's 10 ms of
CPU time; a signed token carries the position from one slice to the next. Below 2⁵⁰ the checks use exact
arithmetic with doubles; a file whose p go above 2⁵⁰ is checked with BigInt, which is slower, in slices
of 40 factors. `pull_submissions.py` saves each sieve upload as `Submissions/<id>/TF/results.json` (Mass
Prime Siever format, with every other odd n as `prp`) and `upload.json`, and with `--delete` also clears
uploads that were started more than three days ago but never finished.

The pull script needs the Worker's `ADMIN_TOKEN`, read from the `UPLOAD_ADMIN_TOKEN` environment
variable or from `upload_admin_token.txt` in your home folder. Never commit it.

To deploy the Worker: create a Workers KV namespace, bind it as `SUBMISSIONS`, add the secret
`ADMIN_TOKEN`, and paste `worker/worker.js` into a new Worker (or use `npx wrangler deploy` with the
namespace id filled in `worker/wrangler.toml`). Then put its URL in `upload_endpoint` in
`content/site.json`. After any change to `worker.js`, paste it in again and deploy. `/status` shows
`"sieve": true` once sieve uploads work. `cd worker && npm install && npm test` runs the Worker tests
locally.
