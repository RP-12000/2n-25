# 2ⁿ − 25 Prime Search

A static data site for the search for primes of the form 2ⁿ − 25 ([OEIS A379020](https://oeis.org/A379020)),
in the spirit of mersenne.ca: one page per exponent for every odd n below 10⁷, plus project-wide status,
sieve depth, known primes and a form to upload results. It is served by GitHub Pages straight from this
repository; there is no server-side code except the small upload Worker in `worker/`.

| Page | What it shows |
|---|---|
| `index.html` | Status: the big chart of every odd n below 10⁷, key numbers, active range, outlook, frontier and PRP results since `status_since`, latest results, largest primes |
| `ranges.html` | Work per 1M / 0.2M of n: sieve depth, P-1, PRP, unresolved |
| `exponent.html?n=…` | One n: status, factors, PRP residues, proof, history, neighbourhood |
| `sieve.html` | Sieve depth by range, candidates left, P-1 factor sizes, siever versions |
| `primes.html` | Every known n, against the expected count |
| `history.html` | The whole story: frontier and work per day since 2024, records, month by month, milestones, timeline |
| `join.html` | How to help, example work lines, upload form |

## Layout

```
*.html               the seven pages (generated by tools/make_pages.py from pages/*.body.html)
assets/              CSS and one script per page; no libraries
content/site.json    facts written by hand: plans, sieve assignments, benchmarks, notes
data/                written by tools/build.py; the pages read only these JSON files
archive/             local copy of what build.py needs from the project archive (not published)
archive/pm1_splits.json     prime factors of composite P-1 results, worked out once by build.py
tools/sync_archive.py       refreshes archive/ from the archive drive
tools/build.py       reads archive/, checks it, writes data/
tools/pull_submissions.py   copies uploads from the Worker into archive/Submissions
tools/make_pages.py  rebuilds the HTML pages after a change to pages/ or the shared header
worker/              Cloudflare Worker that receives uploads (deployed separately)
```

## Updating the site

```
python tools/sync_archive.py                  # when the archive drive is attached
python tools/pull_submissions.py --delete     # only if people uploaded results
python tools/build.py                         # reads archive/, writes data/
git add data content && git commit -m "Update data" && git push
python tools/sync_archive.py --back           # when the drive is attached: copy saved uploads to it
```

On Windows, write `py -3` instead of `python` if `python` opens the Microsoft Store.

All scripts use only the Python standard library. The project archive lives on a drive that is not
always attached, so `build.py` reads `archive/` in this folder, a copy of just the files it needs:
sieve output, candidate lists, and P-1 and PRP result lines for each range folder, plus the uploads.
No proof file is copied. `sync_archive.py` refreshes that copy; it copies a file only when it is new or
changed, never deletes anything, and leaves alone (and lists) a file that is newer here than on the
drive. Range folders are named `3.4M-3.6M` in the copy instead of `3.4M~3.6M`, because some tools
cannot open a path with `~` followed by a digit. `build.py --archive <folder>` reads another copy.
`archive/` is not published.

`build.py` prints a summary. Anything it could not use or did not trust is listed in
`build_report.txt` next to `data/`; that file is not published.

### What build.py checks

* **Sieve output** (Mass Prime Siever 12.0 `results.json`, any number of machines or p slices under
  `Ranges/<range>/TF/`): every factor in `factored` must lie in the file's `[P0, P1)`, divide 2ⁿ − 25,
  be prime (exact test), and not be 2ⁿ − 25 itself. An n counts as removed only when one of its factors
  passes; otherwise it stays a candidate and is listed in the report. Every odd n must appear exactly
  once in `prp` or `factored`, the p ranges of the slices must join up without gaps, and every survivor
  must be in `Candidates/*.txt`, or the report says which n still need a PRP test.
* **Prime95 results**: duplicate lines, n outside their range folder, unknown work types.
* **P-1 factors** must divide 2ⁿ − 25 and lie above the sieve depth of their range. When a run finds
  two or more primes at once, Prime95 reports their product; `build.py` splits it by replaying the
  run's P-1 in small steps on that number alone, and keeps the result in `archive/pm1_splits.json`
  (the first build takes about a minute, later ones a few seconds). The exponent page shows the
  product and its primes, and the statistics count primes.
* **Uploads**: a probable prime reported by someone else is shown as *being verified* until its n is
  added to `confirmed_primes` in `content/site.json` (after re-running the test) or a P result for it
  appears in the archive. A claimed probable prime with a prime factor below 10⁶ is ignored.
* **Uploaded sieve output** (`Submissions/<id>/TF/`) is merged into the range folders that have Mass
  Prime Siever output of their own, and every factor is checked the same way. Its checked factors
  always strike n out. It counts toward the sieve depth only if it found at least 80% of the factors
  expected for its p range (about odd n × ln(ln P1 / ln P0)), or once its id is in
  `accepted_sieve_uploads` in `content/site.json`; otherwise the report lists it. Who found a factor
  above 10⁷ is shown on the exponent page.

## Uploads

The Join page posts `results.json.txt` lines to the Worker in `worker/`, which checks each line, keeps
it in Workers KV, and asks for the proof file when a line reports a probable prime. `pull_submissions.py`
saves each upload as `Submissions/<id>/submission.json` (and `<n>.proof`) in `archive/`, checks proof
files against the MD5 in their result line, and with `--delete` removes from the Worker only what it
saved and checked.

Sieve output (Mass Prime Siever `results.json`, p below 2⁵⁰, plus `siever.log` for the run time) has its
own form. The browser checks every factor and that every odd n appears once, and refuses the file if
anything is wrong. It then sends one line `n p p …` per odd n that has a factor, in uploads of at most
3 MB split by n. The Worker stores the lines once and checks every factor again in slices of 150 factors
(`/tf/begin`, `/tf/check`, `/tf/finish`), which keeps each request well inside the free plan's 10 ms of
CPU time; a signed token carries the position from one slice to the next. `pull_submissions.py` saves
each sieve upload as `Submissions/<id>/TF/results.json` (Mass Prime Siever format, with every other odd
n as `prp`) and `upload.json`, and with `--delete` also clears uploads that were started more than three
days ago but never finished.

The pull script needs the Worker's `ADMIN_TOKEN`, read from the `UPLOAD_ADMIN_TOKEN` environment
variable or from `upload_admin_token.txt` in your home folder. Never commit it.

To deploy the Worker: create a Workers KV namespace, bind it as `SUBMISSIONS`, add the secret
`ADMIN_TOKEN`, and paste `worker/worker.js` into a new Worker (or use `npx wrangler deploy` with the
namespace id filled in `worker/wrangler.toml`). Then put its URL in `upload_endpoint` in
`content/site.json`. After any change to `worker.js`, paste it in again and deploy. `/status` shows
`"sieve": true` once sieve uploads work. `cd worker && npm install && npm test` runs the Worker tests
locally.
